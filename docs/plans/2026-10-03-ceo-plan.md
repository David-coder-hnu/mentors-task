## C8 为什么与 R#3 的注册表不是一回事

R#3 砍掉的是**策略注册表**——它的服务对象是「第三方策略作者」，而这个项目只有一个作者，所以它的间接层（入口点发现、版本协商、规则 schema）没有用户。

C8 保留的是** shim 的合成规则表**，它的服务对象是**实验本身**：门 2 条件 1 要求 shim 覆盖 `Method` / `Protocol` / `Hop` / `Goal` 四维，这四维必须能独立替换才能分别检验。所以它的形态是**一张 dict + 一个 dispatch 函数**（数据表），**不是**带入口点与版本协商的注册表。

**这是一次对用户 C8 选择的收窄，不是撤销**——与 #R3 同类，但理由不同（内容可替换 ≠ 插件生态）。

**门 0 → 门 1 的通过条件**：

1. **容器化靶场能起来（T1 的 Verify）**——`--cap-add=NET_ADMIN --cap-add=NET_RAW` 下从任一 netns ping 配置前缀能收到回包；
   > **（OV-7）并且要过「确定性」这道可度量的验收，光「能收到回包」不算通过。** Docker 路线（D4.1）把靶场放进了一个**虚拟化的 VM 网络栈**，而 Punching Bag 是对**速率**敏感的（`--max-queue-size` 默认 250k，`论文：>60 kpps 拥塞`）。`:13` 的确定性是「用目的地址的哈希 mod 100 决定回不回包」——**那是靶场的决定，不是包的送达**；在 VM 网络栈里，一个被决定回应的包仍可能因为队列、调度或 veth 抖动而丢在前端。这正是我在迭代 3 的 6A 里把可复现重述为**日志侧**性质的原因——但那一步是在**承认**时序不确定性，不是**消除**它；如果 Docker 的不确定性大到污染观测，重述就只是把问题写得更体面。
   > **可度量的验收（三条，全绿才算过）**：
   > - **重复运行的实收计数差**：同一 config、同一 seed 连跑 3 次，实收包数的**最大值与最小值之差 / 均值 ≤ 1%**；

   > - **拥塞余量**：实测 peak rate 与靶场拥塞点（~60 kpps）的比值，留 ≥2× 余量。
   > **任一条不过 ⇒ Docker 判定为不可用，立即转 WSL2 / Linux 机器**，不等条件 5 再暴露。理由：这三条测的是**场地质量**，而场地质量不能等到「对账做不出来」才发现——那时已经写完 adaptor 了。
2. golden 抓包已入库；
3. **`GroundTruth` 导出正确（T3 的 Verify）**——手工小 config 逐字段比对，且显式断言「未配置前缀」与「rate==0 前缀」是两个不同集合；
   > **并且（Section 5B）：`ground_truth.py` 拥有「哪些前缀算 aliased」的唯一定义。** 评分器、主端点、shim 契约**只能调用它**，不得各自重判。理由：`:658` 已承认这个映射「是我们自己定的、**且承重**」，`:525` 又说四档规则未知、aliased 与 EUI-64 前缀「长得很像」。四处各判一次，只要两处对边界情形（如 rate=0.9）取法不同，**主端点会静默给出两个数**——而主端点是判胜负的依据，分叉即结论不可复现。这条同时是 DRY 与 D7 隔离的同向要求：真值的**解释权**应与真值的**访问权**同侧。
4. `--dump-truth` 在手工 config 上输出正确；
5. **0.2(a) 有明确答案，且答案是「逐包日志可用」（Section 6B——已从软条件升级为硬条件）**。原写法是「是或否都算通过」，**错在没接上下游**：T2 的 Verify 是「集成测试断言 实收==已发」，而那个对账只能靠这份日志。若答案是「否」，`:524` 说要给上游打补丁——那是一个**无估算的 C++ 改动**，且它**已在门 1 的关键路径上**（没有对账就无法证明数据未被丢包污染，而未对账的数据不能用来算分）。把它留作软问题，等于把上游依赖排在它自己的下游，与迭代 3 已修的 T8 依赖倒置是同一类错误；
   > **（OV-6）首选路径改了：先在容器 veth 侧自己抓包计数，上游补丁降为退路。**
   > 上一版把「给上游打补丁读它的逐包日志」当成主要出路，而那条路要**读第三方源码 + 写 C++**，且**没有任何估算**——于是它自动成了门 0 关键路径上最重的一块。但条件 1 已经要求 `CAP_NET_RAW`，而**有了这个能力，`tcpdump` / `dumpcap` 就能在 veth 上直接数包**。那个对账要回答的问题只是「**实收 == 已发？**」——一个**计数**问题，不需要钻进靶场内部。
   > **三条闭合方式，按优先级**：
   > - **(i) 【首选】veth 侧抓包对账**——不读第三方源码、不写 C++、不新增上游依赖。**门 0 的条件 5 以此判过。** 这也让门 0 的上限回到可控范围（不再挂一个无估算的 C++ 改动）。
   > - **(ii) 上游逐包日志存在**——直接通过；
   > - **(iii) 【退路】上游补丁已落地并跑通一次对账**——仅当 (i) 在实测中被证明不可行（例如容器内 veth 名不可预测、或抓包本身成为瓶颈）时才走，**且成本必须回填进门 0 的上限**。
