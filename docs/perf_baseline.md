# 靶场吞吐基线（T2(b)）

**日期**：2026-10-08　**环境**：Docker Desktop / Windows 11，compose 网络 `pbnet`
**探头**：`src/adapter/probe_pool.ProbePool` + `RawIcmp6Iface`（原始 ICMPv6 套接字）
**靶场**：Punching Bag @ `cfe60b3e`，`--thread-count=2`，前缀 `2001:db8:dead::/64` rate 1.0

---

## 一、结论

| 问题 | 答案 |
|---|---|
| **无丢包的最大在途数** | **512** |
| 该档吞吐 | **≈ 4 850 pps**（count=20000 用时 4.12 s） |
| 实测吞吐上界 | ≈ 16 800 pps（池大小 ≥ 4096），但**该档丢 8%~24% 的回包且全程静默** |
| 瓶颈 | 不是靶场，不是网桥，是**本机内核的套接字接收队列** |
| `SO_RCVBUF` 实得 | **425984 字节**（请求 1 MiB / 8 MiB / 64 MiB 都是这个数） |

**对实验的硬约束**：池大小必须 ≤ 512。超过它，回包集合会随机器负载变化，
**判据 6(i)（同一 config + seed ⇒ 回包集合逐次完全相同）直接不成立**。
这不是「性能调优」，是「整轮实验可不可信」的分界线。

**站内可用的吞吐预算 ≈ 4.8 kpps**。设计方案原先设想的「超过 60 kpps 会填满靶场队列」
这个数量级在本环境里**根本到不了**——实测最大值 16.8 kpps，而且要到那个数
必须接受静默丢包。

## 二、一个必须先讲的坑：读账本的时机

靶场的 `packet_log.txt` **只在正常退出时 flush**（`punchingbag.cpp:386`）。
在靶场还活着的时候去读，读到的是**被截断的文件**，于是「我们发了 2000、文件里只有 300 行」
会被对账读成**第一层丢包 1700 个**——而那 1700 个丢包**根本不存在**。

**这个假报的方向最坏**：它把结论推向「这个环境很慢、池子要开得很小」，
而那是**保守**结论。保守结论不会有人去质疑，所以它会留下来。

所以每一档固定四步，顺序不可换：`① recreate 靶场 → ② 跑探测 → ③ **停靶场** → ④ 读账本`。
`perf_sweep.py` 把这四步写死了。

## 四、第四层丢包：回包在回来的路上丢的

### 4.1 现象

`pool = 16384` 那一档：

- 靶场账本：`captured = 20000`、`enqueued = 20000`、`libnet_errors = 0` —— **三层全清**
- 我们收到：**4157**
- 对账器（`range_logs.reconcile`）判决：**通过**

少掉的 15843 个回包，在**靶场的任何日志里不留痕，在我们的任何计数器里也不留痕**。

### 4.2 定位：在 eth0 上独立抓包

三个候选的解释，应用层症状**完全一样**（都是「这个地址没回包」），
但实验含义相反——①②是靶场的问题（该换环境），③是我们自己的问题（该改代码）：

  ① 靶场根本发不出去　② 发了，在 bridge/veth 上丢了　③ 到了本机网卡，被内核丢了

`scripts/perf_wire.py` 起 `tcpdump` 在 harness 容器自己的 eth0 上数
Echo Reply 的帧——**独立于我们那个套接字**。结果：

| 池大小 | tcpdump 在 eth0 数到 | 我们的套接字收到 | tcpdump 自己丢帧 |
|---:|---:|---:|---:|
| 4096 | **20000** | 16104 | 0 |
| 16384 | **20000** | 5532 | 0 |

**20000 个回包全部到达了本机网卡。** ①②当场出局，丢在 ③：
容器内核的原始套接字接收队列。

### 4.3 为什么队列会满：回包是**簇状**到达的

同一轮抓包的到达时间戳统计：

| 池大小 | 全部到齐耗时 | 最猛 1 ms 内 | 最猛 5 ms 内 | 相邻帧间隔中位数 |
|---:|---:|---:|---:|---:|
| 4096 | 1.154 s | 482 帧 | 1300 帧 | 4.1 µs |
| 16384 | **0.235 s** | 473 帧 | 2048 帧 | **2.9 µs** |

靶场的 `pcap_open_live(..., 100, ...)` 第 4 个参数是 **100 ms 读超时**，
它在每个节拍上把攒下的请求批量应答。于是 20000 个回包在 235 ms 内到齐
（≈85 kpps 均值，峰值 473 kpps）。装不下的**尾丢弃**。

**队列到底装得下多少个？** 缓冲区是 425984 字节，而**内核按 skb 的 `truesize`
记账，不是按线上帧长**——一个 62 字节的 Echo Reply（IPv6 头 40 + ICMPv6 头 8 +
载荷 12 + L2）在 `struct sk_buff` 里要占大约 800 字节（头 + `skb_shared_info` + 对齐）。
所以容量大约是 **500~550 个**，而不是按帧长算出来的 7000 个。

> **这个数只有「吻合」，没有「推导」**：`truesize` 我们没有直接测过，
> 它是由**实测边界**（512 干净 / 640 有丢）反推出来的。写在这里是为了让
> 「512 这个上界是从哪来的」有个可检验的解释，而不是一个孤立数字。
> 真要坐实它，得读 `/proc/net/sockstat` 或 `ss -m` 的 `skmem` 字段。

### 4.4 我们自己的那半个原因（已修）

`ProbePool.run` 原先的结构是 **「先把整窗发满，再去收」**：
填窗循环里一次 `recv_available()` 都不调。填满 16384 个在途要花几十毫秒，
**这几十毫秒里一个包都不收**——正好是回包开始涌入的时刻。而那个队列只装得下
约 500~550 个 skb（见 4.3），几毫秒的簇就能把剩余空间吃光。

修法：填窗途中每 32 个包回头收一次（`drain_every_sends`，默认 32）。
代价是每 32 次 `sendto` 多一次必然 `EAGAIN` 的 `recvmsg`。

| 池大小 | 修前实收 | 修后实收 | 线上帧数 |
|---:|---:|---:|---:|
| 4096 | 16104 | **19093** | 20000 |
| 16384 | 5532 | **18244** | 20000 |

单测把这条钉住了：`tests/unit/test_probe_pool.py::TestDrainDuringFill`
用一个**容量有限的假收件箱**（尾丢弃、不留痕）复现同一个机制，
并配了反向对照（把节拍拉宽到超过整窗，丢包原样回来）——
证明「边填边收」既是充分的也是必要的。

### 4.5 剩下的那一成：是环境的，不是我们的

修完之后 `pool ≥ 4096` 仍丢 8%~10%。**两个独立旋钮都推不动它**：

| 试过的 | 结果 |
|---|---|
| `poll_interval_s = 0.001 / 0.0002 / 0.0`（含忙等） | 无改善（17139 vs 17950） |
| `drain_every_sends = 32 → 4` | **反而更差**（16781） |

节拍收紧反而更差，说明瓶颈不在我们的排空频率，而在
**两次排空之间到达的簇高度**超过队列容量。而容量那个旋钮拧不动：

**`SO_RCVBUF` 被钉死在 425984 字节。** 请求 1 MiB / 8 MiB / 64 MiB 都是这个数。
上限来自 `net.core.rmem_max`，而它是**全局 sysctl**（非 per-netns）——
容器里 `/proc/sys/net/core/` 下**根本看不到这个文件**，
`docker compose run --privileged` 又不被支持。所以这一档**在本环境内无法抬高**。

因此：**残余丢包是本环境的固有属性**，实验口径按 512 走。

## 五、几个负结果（别重复试）

- **忙等排空（`poll_interval_s=0`）**：修前修后都无显著改善。池子的轮询节拍
  不是高并发丢包的原因。
- **收紧 `drain_every_sends`**：4 比 32 更差。它只在**填窗阶段**有用，
  填完之后由队列容量决定。
- **抬高 `SO_RCVBUF`**：容器内做不到，理由见 4.5。
- **`pool = 32768`**：修前实测 5055/20000、17682 pps。在途数超过约 2 万
  （= count）之后池子不再是瓶颈，`count` 才是——再加在途数只是白占内存。

## 六、顺带发现的一条（与吞吐无关，但会误导判断）

`ProbeRun.foreign_replies` 在**每一轮都非零**（1~5 个），即使当轮所有探测都被认领。
来源大概率是网桥上的环境 ICMPv6（邻居发现 / 路由通告），它们落进了
「不属于本轮的回包」这个桶。

**后果**：`foreign_replies` **不能**当作「另有一个探测器在跑」的信号读。
真要那个信号，得先按 ICMP 类型过滤（Echo Reply 之外的不该进这个计数）。

## 七、怎么复现

```bash
# 四步式的完整扫描（宿主侧编排，含停靶场、读账本、四层对账）
cd docker
python ../scripts/perf_sweep.py --levels 256,512,640,768,896,1024 --count 20000

# 单档 + 线上抓包对账（定位第四层用）
docker compose --profile harness run --rm harness \
  python -m scripts.perf_wire --pool-size 16384 --count 20000 --recv-bufsize 1048576

# 单档标定（不读账本，只看 pps 与 rtt 分布）
docker compose --profile harness run --rm harness \
  python -m scripts.perf_calibrate --pool-size 512 --count 20000
```

判据 `clean` 现在是**四层**：靶场三层 + `lost_reply_path`。
后者是一条**经验**判据（`sent - received`），成立的前提是靶场配成 rate 1.0。
**换配置时必须重判**：rate < 1.0 时靶场只对确定性子集回包，
正确的式子是 `预期回包数 - 实收数`，而不是 `sent - received`。

## 八、还没做的

- **本环境只能测到 16.8 kpps。** 设计方案设想的 60 kpps 量级没验证过，
  而它关系到「靶场队列满」那条失效路径会不会被触发。要测需要更大的在途数
  与更快的靶场，或者接受「本环境测不到那一档」并写进实验口径。
- **换一个 `SO_RCVBUF` 更大的环境（Linux 宿主）后，512 这个数会变。**
  上界与 `SO_RCVBUF` 相关，但这个关系目前只有两点（512 干净 / 640 有丢），
  还不足以写成公式——而且 640 丢 148、1024 只丢 36，**非单调**，
  说明它是一条软阈值（取决于两次排空之间到达的簇高），不是一条硬容量线。
  换环境后要重新扫，不要照搬 512。
